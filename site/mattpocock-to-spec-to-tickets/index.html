Matt Pocock skill explainer · mattpocock/skills

mattpocock/to-spec → to-tickets

Two skills that turn a finished conversation into a published spec, then a graph of tracer-bullet tickets.

to-spec: Do NOT interview the user; just synthesize what you already know. to-tickets: Break a plan, spec, or conversation into a set of tickets: tracer-bullet vertical slices, each declaring the tickets that block it. implement-spec then builds the graph.

Who it is for

You have already grilled the idea (or charted it with wayfinder) and want it on the tracker as work an agent can grab.

What you get

One spec issue, N ticket issues (or .scratch files) with blocking edges, all labelled ready-for-agent.

Why It Exists

Talk First, Then Write It Down Once

Both skills refuse to start from nothing: they synthesize what the conversation already holds.

1

This skill takes the current conversation context and codebase understanding and produces a spec.

2

Work from whatever is already in the conversation context.

3

"Make the change easy, then make the easy change."

4

Do NOT include specific file paths or code snippets. They may end up being outdated very quickly.

Mental Model

A Spec Is The What; Tickets Are A Task Graph

Seams

The fewer seams across the codebase, the better - the ideal number is one.

Tracer bullets

Each slice cuts a narrow but COMPLETE path through every layer (schema, API, UI, tests): vertical, NOT a horizontal slice of one layer

Size

Each slice is sized to fit in a single fresh context window

Graph

The tickets are not a list of steps. They are a task graph with blocking relationships between them.

## Problem Statement
## Solution
## User Stories        (a LONG, numbered list)
## Implementation Decisions
## Testing Decisions
## Out of Scope
## Further Notes

The to-spec template headings.

The Flow

One Conversation Becomes A Merged Branch

  1. grill Talk it through

    grill-with-docs or a finished wayfinder map

  2. /to-spec Publish the spec

    template + ready-for-agent

  3. /to-tickets Publish the graph

    quiz, then blockers first

  4. /implement-spec Build in parallel

    worktrees + tdd + merger + code-review

Gotchas

Where The Text Disagrees With Itself

From reading every file at 5beb35b. No scripts ship, and nothing was run against a live tracker.

Gap README says to-spec quizzes you

The README’s workflow list says quizzes you about which modules you're touching before creating a spec, but its own skill list says No interview, just synthesizes what you've already discussed. The skill sits between: no interview, one seam check.

Gap ready-for-agent may not exist

Both skills apply ready-for-agent, but setup only writes the label vocabulary in Section B, and only when the triage skill is installed. Without it the label may be missing on your tracker.

Gap “tracker doc’s operation” for sub-issues

to-tickets says to make each ticket a sub-issue via the tracker doc, but only the GitHub tracker doc defines a sub-issue operation; the GitLab and local docs do not.

Cost Context-window sizing is a judgment call

“A single fresh context window” is not measured; size slices by feel or borrow wayfinder’s 100K-token yardstick.

Copy No file paths in specs

Specs and tickets stay valid while code moves. Prototype snippets are the only allowed exception.
