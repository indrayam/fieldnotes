pstack

“if you want to go fast, go deep first.”

pstack is Lauren Tan’s (poteto) pack of agent skills for Cursor, MIT licensed, living in cursor/plugins/pstack. One router skill, /poteto-mode, picks a playbook for your task and pulls in the other skills and principles as its steps need them. The README’s goal: “pstack helps you write less, but higher quality code.” This page covers the tree as of the latest commit and checks its scripts by running them.

TL;DR

TL;DR

  • Install with /add-plugin pstack, run /setup-pstack once, then start real work with /poteto-mode.
  • Every one of the 56 skills sets disable-model-invocation: true. Nothing fires on its own: you type a slash command, or /poteto-mode reads a skill file by path when a step needs it.
  • Work is split by model: code delegates go to Grok (grok-4.7-xhigh-fast), judgment and prose go to Opus (claude-opus-5-5-xhigh). Panels (arena, architect, interrogate) run one subagent per listed model.
  • The rule that runs through all of it: prove it on the real artifact. Tests alone don’t count as verification.
  • New since v0.15.25: formal verification (/create-formal-verification-skill, /maintain-formal-verification-skill), a Claude Code install, a docs-vs-tree check, and a reworked /sharpen and /ketchup.
README.md

Why it exists

The README begins with a complaint: “ai writes too much slop code… throughput without quality is not a goal i aspire to.” Her answer has two parts. First, go deep on one agent so you can trust its output. Second, once you trust it, run many agents in parallel (“fearless parallelism”). A model is chosen for each role because “every frontier model has its strengths and weaknesses.”

No planning skill, on purpose

“personally, i don’t believe in planning. the best spec is code.” Cursor’s plan mode covers planning, and poteto-mode has a multi-phase-plan playbook, but planning isn’t the default.

skills/poteto-mode/SKILL.md

Mental model

Think of it as a router, playbooks, tools, and rules. The playbook picks the steps, the workflow skills do the heavy work through subagents, the principles constrain the choices, and nothing counts until it’s proven.

Bundled skills resolve as ../<name>/SKILL.md from the router, so the router hands its own absolute path to every poteto-agent prompt.

poteto-mode “Non-negotiables”

How it works

  1. Match a playbook. The router opens a todo list whose first items are the playbook’s steps, copied in word for word.
  2. Fire triggers. A nontrivial change triggers how. Code that crosses a function boundary triggers architect. A contested design triggers interrogate. Parallel work goes to swarm or arena. Any prose triggers unslop. A measured number triggers benchmark-checklist. Before review, no-comments runs. Long or unattended work triggers show-me-your-work.
  3. Don’t ask what you can observe. Before asking “which approach?”, the router checks whether running something would answer it. If so, it builds a sketch with the prototype playbook. Only real product or preference calls go to the human.
  4. Cite principles. The reply names each principle that changed a decision. It may cite only principles whose leaf SKILL.md it read in this session.
  5. Prove and ship. check-plan.mjs enforces the rule that “a PR is verified only when its unit, live, and perf boxes are all checked”. Every playbook ends with opening-a-pr.

skills/principle-* · 24

Principles

Each principle is a short rule, 9 to 34 lines long. The router groups them into the five headings below. Each one is invoked as principle-<name>.

PrincipleWhen it applies (frontmatter)
Core · 10
laziness-protocolApply when refactoring, evaluating diff size, or tempted to add abstractions, layers, or signal threading. Bias toward deletion and the smallest change that solves the problem.
foundational-thinkingApply before writing logic: choosing core types and data structures, sequencing scaffold-vs-feature work, asking what concurrent actors share. Get the data structures right so downstream code becomes obvious.
redesign-from-first-principlesApply when integrating a new requirement into an existing design.
attack-the-premiseApply when two or more fixes that share one premise have failed the same gate. Write the premise down and test it directly before you write another fix that assumes it.
subtract-before-you-addApply when sequencing an addition, refactor, or rewrite. Remove dead code, redundant validators, and stub references first, then build on the simpler base.
minimize-reader-loadApply when reviewing or shaping code that's hard to trace. Count layers between question and answer, and hidden state in the reader's head; collapse one-caller wrappers and shrink mutable scope.
outcome-oriented-executionApply during planned rewrites and migrations with explicit phase boundaries. Converge on the target architecture; don't preserve smooth intermediate states with throwaway compatibility code.
experience-firstApply when product, UX, or feature-scope tradeoffs come up. Choose user delight over implementation convenience; ship fewer polished features over more rough ones.
exhaust-the-design-spaceApply when facing a novel UI interaction or architectural decision with no precedent in the codebase. Build 2-3 competing prototypes and compare side by side before committing.
build-the-leverApply to any non-trivial work, not just bulk work: edits, migrations, analyses, checks. Build the tool that does it or proves it (codemod, script, generator, or a skill your subagents follow) instead of working by hand. The tool is the artifact a reviewer can rerun.
Architecture · 6
model-the-domainApply when writing stateful logic, or when code branches a lot or repeats a shape assumption across files.
boundary-disciplineApply when wiring validation, error handling, or framework adapters. Concentrate guards at system boundaries (CLI, config, network, external APIs); trust internal types and keep business logic in pure functions.
type-system-disciplineApply when designing types, reviewing a function signature, or writing code in any statically-typed language. Make illegal states unrepresentable, brand semantic primitives, parse external data at boundaries, exhaust variants, derive from authoritative schemas.
make-operations-idempotentApply when designing commands, lifecycle steps, or processing loops that run amid crashes, restarts, and retries. Converge to the same end state regardless of partial prior runs.
migrate-callers-then-delete-legacy-apisApply when introducing a new internal API while old callers still exist. Migrate callers and delete the old API in the same wave instead of preserving compatibility layers.
separate-before-serializing-shared-stateApply when concurrent actors might write to the same file, branch, key, or state object. Eliminate the sharing first; serialize structurally only when one shared writer is a real invariant.
Verification · 5
prove-it-worksApply after completing a task, before declaring done. Verify against the real artifact (run the feature, read the actual value, inspect the diff), not a proxy, self-report, or 'it compiles.'
fix-root-causesApply when debugging. Trace each symptom back to the first place the system went wrong and fix it there. A guard is a fix only when the state it handles is legitimate.
sequence-verifiable-unitsApply to multi-step work (sweeps, migrations, runs of similar edits) and to how you stack commits and PRs. Break work into small units that each end in a verifiable state, check each before the next, and order delivery so the sequence proves itself to a reviewer.
test-behavior-not-implementationApply when you write, change, or keep a test. Assert what the code's users can observe, so that the test fails when that behavior breaks and keeps passing when only the internals change.
explain-the-numberApply before you trust, report, or act on a number you measured: a speedup, a regression, a throughput, a latency, or an eval result. Find what limits it, and rule out that it measured something other than the work you think.
Delegation · 2
guard-the-context-windowApply when context is filling up: large outputs, long files, repeated reads, fan-out planning. Route bulk to subagents; keep summaries in the main thread, not raw payloads.
never-block-on-the-humanApply when tempted to ask 'should I do X?' on reversible work.
Meta · 1
encode-lessons-in-structureApply when you catch yourself writing the same instruction a second time, or notice a recurring correction. Encode the rule as a lint, metadata flag, runtime check, or script instead of more text.

README · skills/setup-pstack/SKILL.md

Install and setup

/add-plugin pstack                      # Cursor
/plugin marketplace add cursor/plugins  # Claude Code
/plugin install pstack@cursor-plugins   # → commands become /pstack:<name>

/setup-pstack does the following:

  1. Detects which model slugs you can pass to a Task subagent.
  2. Asks for a budget: unlimited=max, large=xhigh (the default), medium=high, small=medium.
  3. Shows each role with its model and asks you to confirm.
  4. Validates that every slug was detected.
  5. Overwrites ~/.cursor/rules/pstack-models.mdc with alwaysApply: true.
  6. Offers /create-verification-skill once, then /create-formal-verification-skill once.
# budget: large (xhigh)
feature, refactoring: grok-4.7-xhigh-fast
judgment and prose: claude-opus-5-5-xhigh
arena runners: claude-opus-5-5-xhigh, grok-4.7-xhigh-fast
interrogate reviewers: claude-opus-5-5-xhigh, grok-4.7-xhigh-fast
swarm workers: grok-4.7-xhigh-fast

An excerpt of the default rule shape (17 role lines in full). Grok tops out at xhigh, so unlimited keeps Grok at xhigh.

Stale defaults

A rule file written before a default changed still pins the old default. Delete those role lines, or the whole file, and run /setup-pstack again. A rerun keeps any role you set to something other than the default.

Not bundled

deslop, control-cli and control-ui ship in cursor-team-kit. /create-skill is built into Cursor. The router calls all of them, so install cursor-team-kit to get the full set.

Gotchas and findings

1

“Use when…” never triggers on its own. All 56 SKILL.md files set disable-model-invocation: true, including typescript-best-practices (“Use when reading or editing any .ts”) and tdd. Those descriptions read like auto-triggers, but these skills only run from a slash command or when the router reads them. This is a gap between the docs and the behavior.

2

Three principles say only when, not what. The descriptions of model-the-domain, never-block-on-the-human and redesign-from-first-principles give the trigger but not the rule. The router’s index fills that in.

3

One flaky cold test run. The first bun test (Bun 1.4.2) reported 59 pass, 1 fail and 1 error across 60 tests. Five reruns all passed 68/68. I didn’t capture the failing test, so I can’t say which one it was.

4

Side effects. /setup-pstack overwrites ~/.cursor/rules/pstack-models.mdc, which applies to every project. The log.sh script creates the parent directory of the log file. The verification skills generate new project-local skills and open PRs. Babysit stops at merge-ready and never merges. Shipping merges when you ask it to land (bottom-up, gh pr merge --squash, may arm auto-merge and --force-with-lease the next PR). Autopilot-full owners merge granted queue items after swarm verification; autopilot-stack never merges.

5

Grok Bot–specific skill. /make-bot-ui builds a webhook UI that wakes a Grok Bot, with optional Tailscale exposure. It’s the only skill tied to a product other than Cursor.

6

Docs are consistent. The repo’s own scripts/check-pstack-docs.mjs reports “56 skills (32 commands, 24 principles), 23 playbooks, 2 agents … 0 problems”. generate-pstack-harness-trees.mjs --check reports “harness/pstack is up to date”. Every skill name matches its folder (fixed in #702).
